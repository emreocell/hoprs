# Plans 1–3: follow-ups for later plans

Plan 1 (foundation and transfer engine), Plan 2 (SSH and SFTP) and Plan 3 (FTP and FTPS, branch `plan-3-ftp-ftps`) are done. Reviews raised the items below, and they were left for later plans on purpose. Each says when it has to be fixed.

# Plan 1

## Fix before Plan 5 (UI)

- **Event resync.** Expanding a large folder emits one `Added` event per entry into a 1024-slot broadcast channel. After `Lagged`, `snapshot()` has no sequence number, so a stale buffered `StateChanged` can overwrite newer state. Add sequence numbers to events and snapshots, or batch `Added`. Document "on `Lagged`, re-snapshot".
- **`TransferEngine::start` cannot report a failed recovery.** A corrupt queue then shows as an empty queue with no signal. Make `start` fallible or emit a startup error event.
- **No clear-finished API.** The actor's `items` map only grows, which conflicts with the idle-memory target in spec §9. Expose `QueueStore::clear_finished` through the engine and prune the actor's maps.
- **No final `Progress` event when a transfer completes or fails.**
- **`pause` then an immediate `resume` on an item that holds a worker slot returns `Conflict`.**
- **An extra `StateChanged(Active)` is emitted when an already-finished folder is reactivated and has nothing pending.**
- **"N items failed" grammar.** The text is fixed by the plan's test. Move it to i18n.
- **A `resolve` choice is lost if the item is paused while still Queued.** The destination is untouched, so with `Ask` the user is asked again.

## Fix before or during Plan 2 (SSH/SFTP)

- **A listing entry with an invalid name fails the whole folder.** Still open after Plan 2. Revisit for hostile servers; it could mark only that entry Failed.

## Hygiene (any time)

- **`state_detail` has three meanings: skip reason, pause origin and override.** Move them into separate columns in a future migration.
- **The dispatch stores only a `Some` override.** Always writing `set_next_policy(id, override)` would remove the dependency on the Queued-row invariant.
- **Test gaps** in `RemotePath` edge cases, io error mapping, MemFs permission and rename refusals, `decide()` with both mtimes `None`, store corner cases, and `copy_file` resume at `offset == size` and `offset > size`.
- **Timing-sensitive tests** (300 ms windows, and `large_tree_is_lazy` panicking on a lagged receiver) may be flaky on the Windows CI runner. Watch them.
- **Windows-specific.** `LocalFs::set_modified` on directories, reserved names (`NUL`, `CON`), and lossy conversion of non-UTF-8 names in `list`.
- **Case-insensitive duplicate names on download (Windows).** Duplicate-name detection in a listing is an exact match, so `A.txt` and `a.txt` from a case-sensitive server both become children and write the same local file on a case-insensitive file system (NTFS, default macOS). Compare names case-insensitively when the local side is case-insensitive.

# Plan 2

## Before Plan 5 (UI)

- **`Unknown` cannot say that other key types are known.** A host known by its ed25519 key that presents only an RSA key is a plain "new host" prompt on a first connect (reconnects are pinned to the first key). `HostKeyStatus::Unknown` and `Prompter::confirm_host_key` should report "other key types are known for this host" so the UI can warn.
- **`learn` writes plain host names.** Ubuntu ships `HashKnownHosts yes`; write hashed entries (`|1|salt|hash`) when the user's config asks for it.
- **`write_atomic` replaces a symlinked `known_hosts`** with a regular file, and does not fsync the directory. A temp-name collision between two writers and a concurrent `learn` being lost are possible too.
- **`remove` deletes whole wildcard or multi-host lines** (as `ssh-keygen -R` does). The UI must warn before removing a line that covers other hosts.
- **Concurrent connects to the same unknown host both prompt and both append.** Serialize prompts per host.
- **Session states for the UI.** `Connecting` is never observable (connect only returns once connected); a failed first connect leaves no session to `reconnect_now`; there is no "waiting for user" state while a reconnect attempt is prompting; a prompted (not saved) password is asked again on every reconnect.

## Before Plan 6 (terminal)

- **`ShellChannel::output()` returns `&mut Receiver`.** An iced `Subscription` needs an owned stream.
- **`ShellChannel::close()` awaits `writer.close()` inline** before stopping the pump.
- **Channel budget.** One metadata channel, up to 8 SFTP stream channels and the PTYs share the server's `MaxSessions` (10 by default). Count them and fail clearly (or queue) instead of hitting the limit.

## Before perf/bench work

- **Small files issue 64 read requests.** Cap the pipeline depth by the size `lstat` returned.
- **The SFTP stream pool mutex is held across a channel open.**

## Before a Windows release

- **Windows compile unverified.** `aws-lc-sys` needs a mingw C compiler; the cross-check could not run locally.

## Later

- **Rekey.** russh 0.65 calls `check_server_key` only on the initial key exchange, not on a rekey. Check whether russh refuses a rekey that presents a different host key; if not, pin it there too.
- `ReconnectPolicy::delays()` edges (`max_attempts` 0, base > max) and `ScriptedPrompter` cancel defaults have no tests.
- `ScriptedPrompter` discards the arguments of its calls, so no test checks the fingerprint passed to `confirm_host_key`.
- `known_hosts::wire_blob` uses `unwrap_or_default`.
- `validate_host` does not reject `[` or `]`.
- `remove` keeps `@revoked` lines (accepted; document it).
- CI could dump the compose logs when the integration job fails.
- The `Unreadable` key skip reason has no test.
- After a connect timeout, the lingering russh task can still show a host-key prompt; add a cancel flag on `WatchedPrompter` instead of only answering "no".
- A tiny race from `tokio::select!`'s random branch order in the connect watchdog.
- Keyboard-interactive answers go to russh as a plain `Vec<String>` (russh API), not zeroized.
- No mock tests for the 10-round keyboard-interactive cap, multi-prompt non-leak or an empty round.
- A single no-echo keyboard-interactive prompt (an OTP, say) receives the configured password once (plan-mandated).
- Agent identities the agent cannot sign with still count against the public key attempt budget.
- `host_key_rotated_blocks_reconnect` may flake if attempt 1 lands in the listener's HUP re-exec window.
- `PipelinedWriter::poll_write` can buffer data and then return `Err` (a second `poll_acks`).
- Pipeline test gaps: a short-then-empty reply at EOF, flush mid-write offsets, an error at flush, a `close()` failure.
- The error detail is lost through `to_io`.
- The `futures-util` requirement should be ≥ 0.3.26 (`push_front`).
- Non-UTF-8 names are decoded lossily (U+FFFD), so that file later fails `NotFound`. Document the limitation.
- `SftpFs` contract edges differ from `LocalFs`: `list` of a dangling symlink, a parent that is a file, `mkdir` through a symlink to a directory.
- The `list` error path can take about 20 s on a timeout (close after `Network`).
- No guard against a server that never sends EOF on a listing.
- A failed `rename` names only `from` in its error.
- No test of concurrent use right after a reconnect.
- The `request_timeouts` unit test is tautological.
- Closing a reader at EOF can wait up to 600 s on a wedged link.
- Docker tests make blocking `docker` calls inside async tests and rely on the multi-thread runtime.
- No restart test for a stored duplicate-name child.
- The duplicate-name marker is the persisted message (renaming it would re-enable retries; tests pin the literal).
- Overlong doc line in `engine/dirs.rs` (`expand`).
- `ShellChannel::overflowed()` is `doc(hidden)`; it could be `cfg(feature = "testing")`.
- The bare-`Eof` (no `Close`) shell path has no test.
- **Resume after a network error assumes the server processed pipelined writes in order.** Both the stop path and `network_requeue` resume from the remote size. This is correct for OpenSSH, but a server that handles writes out of order could leave a hole the resume doesn't see. Either resume from the last contiguously acknowledged offset, or document the in-order assumption on `SftpFs`.
- **A cancel that hits a deferred write error ends `Failed`, not `Cancelled`.** This is deliberate, so the next attempt overwrites. The UI should make it clear.

# Plan 3

## Before merging Plan 3 / before Plan 5 (UI) — open

- **A permanent data channel failure pauses and resumes the site forever.** With an unreachable `PASV` address (`pasv_nat_workaround` off behind NAT), every listing or transfer fails as a `Network` data channel error while the control connection stays `Connected`. The engine pauses the site, `spawn_site_watcher` restores it after its 2 s grace, the item runs again and fails the same way: a loop every `connect_timeout` + 2 s (about 17 s with the defaults), generation unchanged, the item never `Failed`. Reproduced in Task 7 with the engine, the watcher and the `ftps-implicit` service. Options: count consecutive pauses without a new generation and stop restoring (or fail the items) after N, or have the FTP layer report a repeated data channel failure on a healthy control connection as something other than `Network`. The UI must at least show it.

## Before Plan 5 (UI)

- **suppaftp logs `PASS <password>` at trace level.** It logs every command it sends through the `log` crate, the password included. Any logger the app installs must cap the `suppaftp` target below trace (for example `suppaftp=debug`), or use suppaftp's `no-log` feature. The login call in `crates/hoprs-remote/src/ftp/session.rs` carries the same warning.
- **The certificate prompt does not say why the certificate was rejected.** `CertProblem` is only `Untrusted` or `Changed`; an expired certificate, a wrong name and an unknown CA all look alike.
- **A stale pin stays in the profile** (ruling R5): a certificate that chains to a trusted root with the right name is accepted even when a different pin exists, and the old pin is never cleared. Plan 4/5 may clear it.
- **Cancelling an FTP control command causes a visible reconnection.** A command dropped before its reply leaves the control connection in an unknown state, so the session replaces it. Navigation the UI cancels (leaving a folder while it lists) would flicker the connection state; the UI must not cancel these futures, or the session needs a quiet drain/replace.
- **`stat` of a file has no permissions** (ruling R9): it is `SIZE` + `MDTM`, so `mode` is `None`. A properties dialog must take permissions from the parent's listing.

## Before perf/bench work

- **Uploading new files still lists the parent once per file.** Ruling R9 made `stat` of an existing file listing-free (`SIZE`), but the engine's pre-copy `stat` of a missing destination gets `550` and falls back to listing the parent (to tell missing from directory, special file or unreadable parent). Many new small files into a big directory are still quadratic (spec §9). Options: `MLST` when announced, `STAT <path>`, or a short-lived per-directory listing cache shared by the engine's checks.
- A `LIST` slower than `command_timeout` (120 s) on a huge directory or slow link counts as a lost connection and reconnects (ruling R6).
- `with_control` bounds a whole command with `command_timeout`, data connection included. If a config sets `command_timeout` below `connect_timeout`, an unreachable data address times the command out first and is taken as a control loss (reconnect churn) instead of a data channel error. The defaults (120 s / 15 s) are fine; nothing validates the order.

## Logging (any plan that adds a logger)

- `system_roots` drops certificate load errors silently.
- Unparsed `LIST` lines vanish silently: a server with DOS-format listings would show empty folders (or `NotFound`). Log them at debug.

## FTP edges (later)

- Rulings R8/R9: `SIZE` and `STOR` follow symlinks on the server, so `FtpFs` reads or writes a symlink to a file like the file, and `stat` of a symlink to a file reports a `File` (the `RemoteFs` contract says symlinks are never followed; `list` still reports the symlink). Writes to a FIFO are left to the server (vsftpd refuses them). `MLST`, when announced, could tell symlinks apart for the same cost.
- A `522` reply (TLS data connection refused, e.g. `require_ssl_reuse` without resumption) maps to `Protocol` with the reply in the detail. rustls' session cache satisfies vsftpd's `require_ssl_reuse=YES` (tested), so no special hint was added.
- When an upload's data connection fails only at `shutdown` (after every byte was written), suppaftp returns the socket error and drops the server's reply (even a `426`). `FtpFs` then sends a `NOOP`: if the control connection answers, the upload is reported as `Io` ("Upload refused by the server") without the server's reason. It fails safe.
- The `MLSD` path is only unit-tested: vsftpd has no `MLSD`, so it never ran against a real server.
- A `LIST` line whose owner or group is named like a month can be misparsed as a date (rare).
- Children of a symlink to an unreadable directory report `NotFound` instead of `Permission` (documented).
- `stat` under a parent whose listing is a single line costs an extra `stat(parent)` round trip (rare).
- `FtpSession::checkout` does not watch the session state while it opens a connection or checks one with `NOOP`.

## Test gaps and hygiene

- No test that `open_control` sends `TYPE I` and `OPTS UTF8 ON`; `reply_parts` has no non-UTF-8 or multi-line unit test.
- No tests for the supervisor shutting down mid-backoff or for the `InFlight` cancel path.
- The site watcher tests use a `settle()` yield heuristic instead of a deterministic sync point.
- The committed test keys and certificates in `docker/fixtures/ftps` may trip secret scanners; allowlist them before the repo goes public.
